# recon 1.0 — release design

**Date:** 2026-09-11  
**Status:** approved by Pete Richardson on 2026-09-11. Amended on 2026-09-11 to add phase 1b, after phase 1 merged.  
**Next step:** an implementation plan, one per phase

## 1. Why this document

recon is at version 0.1.0. The repository has no tag and no release, and 47 issues are open. This document says which of them 1.0 contains, in what order they are done, and how you know that the release is ready.

## 2. What 1.0 promises

1.0 means that recon is complete and reliable enough to depend on every day. It is **not** a compatibility contract: a 1.x release can still change a key, a flag or a configuration key.

The absence of a contract is the reason for the order of the work. A change that makes a user relearn something must land **before** 1.0, and not after it. A change that only adds something new can wait, because it takes nothing away.

## 4. How the order is decided

Three rules set the phases.

1. **A large change waits for the debt in the files that it touches.** You clean a module one time, and then you change it. This is the reason that #160 comes before #40.

2. **The keymap comes early.** After the actions have names and a user can rebind them, a later key change stops hurting: a user who dislikes 1.1 puts the old key back in the configuration file. #59 is thus the highest-leverage item in the release.

3. **Documentation comes last**, except where a refactor physically moves the text. The nine drift issues describe code that phases 2 to 4 change. If you correct them first, you correct them two times.

### Phase 1b — The live screen (2)

| # | Effort | Title |
|---|---|---|
| #246 | M | In-session log records reach stderr while the TUI holds the alternate screen |
| #245 | M | A background-thread panic tears down the live TUI and consumes the one-shot terminal undo |

Phase 1's review found both of them, after phase 1 merged. They belong together because they obey one rule: while the alternate screen is up, nothing writes to it but the drawing code. #246 gives that rule to the logger, and #245 gives the same rule to the panic hook.

Do #246 first. The panic hook in #245 writes its record through the logger that #246 builds.

**#246.** While recon holds the alternate screen, a log record does not go to stderr. If `RECON_LOG` names a file, every record goes to the file, as it does today. The records at startup and at shutdown keep their present behaviour, because the screen is not up at those times.

**#245.** A panic on a worker thread ends that thread quietly. It does not restore the terminal and it does not print a report, so the screen that the user looks at stays as it is. A panic on the main thread keeps today's behaviour exactly: recon restores the terminal, and then prints the report.

**The cost, which Pete accepted.** With both changes and no `RECON_LOG`, a panic in the scan worker leaves no trace. The user sees only that the marks on the files do not change. `RECON_LOG` makes the panic and its position visible again, in the file.

## 6. Exit criteria

1.0 is ready when all six are true.

1. All 45 issues are closed.
2. No open issue has severity medium or above. This includes an issue that the work itself finds, and not only the 45 issues in the list. #245 and #246 are this criterion at work: phase 1's review found them, both are severity medium, and they became phase 1b.
3. The README describes the code as it is. Today its Known Limitations section cites six issues (#7, #8, #18, #27, #70, #165) that are all closed.
4. CI runs `cargo audit` and the one `#[ignore]`d real-process test.
5. `Cargo.toml` says `version = "1.0.0"` and declares `rust-version`.
6. A git tag and a GitHub release exist. The repository has neither today.

## 7. Risks

**#51 is the largest item.** It needs a background read, because a filter change must not stop the screen on a large file. It is cheaper than its own text says: the issue states that recon has no threading, but recon now has a scan worker (`src/scan.rs:160`) and an editor launcher (`src/editor.rs:518`), both with channels. It is still the item most likely to move the date.

**#40 changes what a filter number means.** `Verdict::Included` becomes a group index and not a filter index. #180 records a trap in that exact area, so phase 3 must correct the document and the code together.

## 8. Decisions and their reasons

| Decision | Reason |
|---|---|
| 1.0 is not a compatibility contract | Pete's choice: 1.0 says "ready for daily use". |
| #46 and #51 stay in 1.0 | Pete's choice. Both were already in the 1.0 milestone. |
| #219 is in 1.0 | Pete's choice: a large improvement for `\| head` on a big file. |
| #224 is in 1.0 | It is the only item that changes an answer a script depends on. A script written for 1.0 would get a different file list in 1.1. |
| #242 is out, but its key is chosen in 1.0 | The feature is additive. The key is not: no letter is free. |
| #19 is out | Pete's choice: a second selection cue is a distraction to maintain. |
| A log record is suppressed while the TUI is up, unless `RECON_LOG` names a file | Pete's choice: a record drawn over the screen costs more than the record is worth, and one variable gets it back. |
| A panic on a worker thread dies quietly, and the main thread keeps today's behaviour | Pete's choice: the screen that a user looks at must survive a thread that a user cannot see. |
| With no `RECON_LOG`, a panic in a worker leaves no trace | Accepted cost. Pete chose it in place of a buffer that holds the records until the screen goes away. |

## 9. After 1.0

1.1 and later take the six deferred issues, and anything new. Because 1.0 makes the actions nameable and rebindable, a key change after 1.0 is a change that a user can undo alone.
